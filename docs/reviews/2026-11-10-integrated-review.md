## 各视角总评

### 模拟

总评（模拟层的正确性与确定性，快照 9da4ceb）：模拟层整体扎实。`npx tsc --noEmit` 干净，`npm test` 120/120 通过。下面这些是逐项量过、确认没问题的：
- 模糊测试：120 局随机构筑，覆盖全部 16 件法宝 × 3 个品阶 × 2 个器灵（共 80 种组合），每局 1–3 人，加上随机的非法指令，一共 157 万帧。没有抛异常，没有 NaN 或 Infinity，没有 id 冲突，帧末也没有残留死敌人。
- 机器人整局巡检：34 局（1/2/4 人、开关 wip、半无敌），共 93 次首领战。阶段流转只出现合法的 `wave→collect→shop→wave` / `→over` / `→win`。每次开波时 `rings`/`knives`/`pending`/`zones`/`orbs`/`gems`/`drops` 都清空，`miasmaInset` 归零，`cleared` 归零。收灵时人物不动，商店里没有没复活的人，每个首领只发一次 `kill`。
- 确定性：`src/sim` 里没有 `Math.random`、`Date` 或浏览器 API；表现层只在 `?wave` 调试路径上用了 `w.rng`。两个 world 交替推进的每帧摘要和各自单独跑的完全一样，说明 `core.ts` 里模块级的空间网格不会在 world 之间串。`tools/balance.ts` 跑 6 个进程，输出的 md5 完全相同。
- 边界都正常：首领换阶段无敌期间，灼烧和流血打不进去，气血卡在 60% 阈值 2.2 秒；灵石为 0 时所有购买和刷新都被拒，`ready` 照常；最后一件公共法宝能卖（乾坤圈卖不掉，卖掉那件的碎片会留着）；第一、二章平定的流程是 `bossDeath → 2.4 秒 → chapterClear/waveEnd → 收灵 → shopOpen`；第三章是 `bossDeath → 2.4 秒 → win`，之后冻结；收灵阶段没有任何伤害来源，人物不会死在收灵里；锁定本身是生效的，刷新和下一次进商店都会保留。

真正的问题集中在四处：
1. 靠墙或在角落时，刷怪被挪回场内，刷到人物身边（major）。
2. 收灵超时的 3 秒裁掉了远处飞来的掉落，违背「不要直接跳到商店」（major）。
3. 首领倒下后的 2.4 秒表现期间，魔气还能把人耗死，结果判负（minor，但一旦发生就是打赢了却输掉整局）。
4. 几处跨波、跨状态没清零的小毛病：火尖枪第二枪、易伤数值、ZONE_CAP、锁定的旧价。

另外有一个潜在的卡死陷阱：网格初值是 0。

关于「同一场景第一次跑和之后跑结果不同」：已复现，并确认不是模拟的问题。原因是 Node 25.9.0（V8 14.1.146.11）在 Maglev→TurboFan 栈上替换（OSR）这条路径上的 JIT 缺陷：`tools/weapon-dps.ts` 的 `run()` 第一次执行时被 OSR 编译，它前后两次返回的两个结果对象（A !== B）的小数字段共用了同一块存储，改 B.dps，A.dps 也跟着变。模拟每帧的完整状态逐位相同。用 `node --no-osr-from-maglev` 跑，或者把循环体挪进单独的函数，都能规避（见 SIM-09）。

两处没有列为问题，只记一下：
- 一阶段一帧打掉超过剩余全部气血时，会先发一次 `kill`、掉 40 颗灵石，再在阈值上「复活」。这在理论上存在，但第一章需要一帧打出 9600 以上的伤害，现有数值远远达不到。
- 联机（M2）里倒在魔气里的人在商店复活后会原地开波，走出魔气要掉一半复活血，等做救援时再一并考虑。

所有脚本都在 <项目目录>/.wt/review/scratch/review-sim/ 下。没有改 src/、docs/、tools/，没有起开发服务器，也没有开浏览器。

### 数值

总体判断：第一章的节奏基本对路，难点集中在后面。到了第二、三章，首领战和精英都不再是「死亡风险波峰」。另外有一个会改变胜负的 bug：负回复不致死（BAL-03）。

**跑法**
- 每组 100 局，用的是游戏实际的商店（只刷画面做好的 8 件；游戏里没打开 WIP.shop）。
- 脚本和输出都在 <项目目录>/.wt/review/scratch/review-balance/，没有改 src、docs、tools 里的任何文件。
- 机器人很会走位和躲招，所以「挨打」的数字是下限。不过把它的反应调到最慢（--skill 0），二、三章首领战挨打中位仍是 0。

**难度曲线**
- 通关 76/100；24 局失败里 19 局死在第一章。
- 第一章首领：用时中位 73 秒，阵亡 8/89，符合「首领战约 70–120 秒、能赢但要挨打」。
- 第二、三章首领：用时中位 56 / 39 秒，挨打中位 0，阵亡 2/80、0/76（BAL-01、BAL-02）。首领五招里四招命中率 ≤ 1%，挨的打 94% 来自横扫。
- 开局前 45 秒没有压力，第一个商店升不了级、多半什么也买不起（BAL-08）。
- 普通波里，掉血三分之二来自法宝够不着的鬼火术士；五种新敌人合计只占约 6%（BAL-06）。

**经济与等级**
- 每波收入：11、24、44、78、116，首领波 125；第二章 67–229；第三章 113–498。整局进账中位约 2700。
- 物价：第 17 波是第 1 波的 2.44 倍。
- 灵石 ÷ 货架四件总价：第 1 波 0.15，第 5 波 1.39，二、三章因为器灵很贵在 0.3–0.8 之间。中后期不算溢出，钱主要流向器灵和灵物。
- 刷新价 3–11 灵石，后期只占收入 2–3%，很便宜；机器人每店最多刷 2 次，所以模拟低估了爱刷新的玩家。
- 首领战开打时的构筑：
  - 第一章：7 级，法宝多是灵灵凡凡；
  - 第二章：12 级，神仙仙灵或仙仙仙仙；
  - 第三章：16 级，神神神仙或神神神神，伤害 +79%、攻速 +36%。
- 等级：第 6 波 8 级，第 12 波 13 级，第 17 波 16 级。暂定的 18 级功法几乎拿不到（BAL-13）。

**物品**
- 聚灵丹明显过强：每店都买，整局多赚约 900 灵石（BAL-09）。
- 血魔珠的代价因为 BAL-03 失效，机器人叠到 3–5 颗也照样通关。
- 其余灵物没看到明显的废品或超模。拾取范围看着没用，其实 +120% 能多 12% 收入；夜明珠前期弱于九转金丹，后期差不多。
- 战场掉落一局约 4 个聚灵符、5 个蟠桃、6 个宝匣。聚灵符一半到手时没有作用，合计不到收入的 1%（BAL-10）。

**法宝**
- 群伤确实都在中位 ±15% 内。
- 打首领的 DPS 差 3–22 倍，现有工具量不出来（BAL-05）。

### 性能

性能与资源泄漏审查做完了，共报 7 条：1 条 blocker、5 条 major、1 条 minor。

最要紧的是 PERF-01，会把整局卡死。放完神通（三头六臂）后 0.3–0.4 秒内陨落再按「再战」（或按 R、点画面），reset() 把冲击波的 Graphics 销毁了，waves 数组却没清空；下一帧调 clear() 抛错，Pixi 的 ticker 从此不再请求下一帧。我用脚本复现了：重开后 5.5 秒 world.time 一直停在 0.1，按方向键人物不动，截图在 scratch/review-perf/freeze-after-restart.png。

**跨局泄漏（PERF-02、PERF-03）**：每次「回到标题」，上一局都整个留在内存里，原因有两个，彼此独立：
- stage、hud、intermission、dialogue 各有一个 window resize 监听从不移除，顺着闭包留住了整局。连续开局 5 次：存活的 Application 1→5、DOM 节点 849→2661、resize 监听 5→21，每局 JS 堆约 +1 MB、渲染进程内存约 +4.5 MB。只摘掉这几个监听，就从 2 局降到 1 局；剩下那 1 局由 main.ts 的 `game` 在标题页期间持有，开下一局时释放。
- 每局的纹理（约 280 条、画布约 29.6 MB）永远留在 Pixi 的全局纹理缓存里，因为 dispose 不销毁纹理。舞台纹理用的是固定种子，每局一模一样，却每局重算约 0.45 秒。

**卡顿热点（PERF-04、PERF-05、PERF-06）**，都在表现层：
- **逐像素笔刷**：火行法宝每帧把 4 800–5 700 个 1×1 矩形重建成 Graphics。首领第三阶段场上只有 3 只敌人，每帧 JS 仍有 6.9 ms，其中约 4 ms 是这一块。改用 pet-fx.ts 里已有的像素缓冲层，孤立测试快约 22 倍。
- **粒子**：没有上限、删除用 splice、对象池只增不减。重场景存活 5k–6.4k 粒，舞台树里有 15k–23.6k 个对象。splice 换成交换删除，60fps 下这一场的粒子更新约从 1.2 ms 降到 0.06 ms；Pixi 渲染时间约 3/4 花在遍历对象上，和可见对象数成正比。
- **雷公鞭**：每次出手现场生成十几到二十几张纹理，出招和落雷那一帧多出 3–10 ms。

**没问题的部分**：
- 模拟本身很省：node 里 280 只敌人时每步平均 0.14–0.39 ms，p99 不超过 1.6 ms。
- 收灵飞约 250 颗灵石时每帧 JS 只有 1.75 ms，暂停时 0.32 ms。
- 一局之内打满 7 波，对象数到峰值就停了，不会一直涨；音频节点在重开之间也稳定。
- 机器人自己的凡品构筑打第 5 波（55 只敌人），每帧只有约 1 ms。

整体看，重场景（四件神品火行 + 280 只敌人）每帧 JS 14–15.6 ms，已经贴着 16.7 ms 的帧预算，手机上一定掉帧。

**测量条件**：Apple M2 Pro，无头 Chromium 加 SwiftShader 软件渲染，同时有别的评审在跑（负载 6–18），绝对值偏高，相对比例可信。无头帧率受 GPU 限制只有 11–18 fps，每帧约跑 3.6 个模拟步，所以按事件触发的开销会比 60fps 下高约 3.6 倍；各模块的 update 和渲染是按帧算的，不受影响。

**建议修复顺序**：
1. PERF-01：清空 waves，tick 加 try/catch 兜底。
2. PERF-02 和 PERF-03：移除监听；确定性纹理做成整个会话只建一次，其余纹理在 dispose 时销毁。
3. PERF-05：交换删除加粒子预算，改动最小、收益最大。
4. PERF-04：笔刷改用像素缓冲。
5. PERF-06：闪电改成预生成的精灵库。
6. PERF-07：界面没变化就不写 DOM。

### 操作流程

整条流程（标题 → 选角 → 开局 → 暂停 / 继续 / 回到标题 → 万宝阁 → 首领 → 战后对白 → 第二章 → 阵亡 / 通关 → 再战）我在 1280×720、1920×1080、844×390@3、667×375@2 四个尺寸下都走通了，键盘、鼠标、触摸三种输入都试过。没有遇到崩溃、卡死或控制台报错，连续三轮「回到标题 → 再开一局」页面元素也没有重复，所以没有 blocker。

做得好的地方：
- 万宝阁的锁、刷新后锁住的货保留、钱不够时置灰加红价加拒绝音效、卖出要二次确认，都按预期工作；锁的状态现在一眼看得清。
- 暂停时所有按键都被拦下；切到后台会自动暂停，回来不会自己继续。
- 对白里第一下空格先补全这一句、第二下才翻页；Esc 跳过对白，不会误开暂停。
- 手机多指正常：按住摇杆时另一根手指能放神通。

问题集中在三类：

1. 适配
   - Retina 屏上画布倍数是奇数时（1280×720、1440×790、1728×1000 这类窗口），顶栏文字叠在一起，很可能就是用户在自己 Mac 上看到的样子。
   - 1080p 全屏反而落到最挤的 480×270 版面、4 倍放大，商店退成三页签。这正是「1080p 太大太粗」的来源。
   - 战斗画面四周是近黑底加 1 像素描边的框，手机上只用了一半到七成屏幕。摇杆在黑边里按下不起作用，神通按钮离拇指太远。

2. 输入被存下或被吞
   - 商店里、战后对白翻完后多按的空格会存到下一波，一开场就把攒满的神通放空。
   - 按住方向键时切走，回来人物会自己一直走。
   - 手机上点法宝看说明，这一下就是「卖」的第一下，再点一次就卖掉了。

3. 过渡
   - 波末场上没有灵石时，收灵和「平定」被一帧硬切掉，正是用户说过不要的「直接跳到商店」。
   - 章节平定横幅在所有尺寸都折成两行。
   - 竖屏提示底下游戏照跑、照样挨打，提示的两行字还挤成了一行。

建议先修 UX-01、02、03、04、06：改动都小、收益最大。然后统一处理画面适配（UX-05、07、08），再顺手收拾阵亡 / 通关面板和万宝阁的信息截断。
