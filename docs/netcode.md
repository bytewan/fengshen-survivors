# 联机（M2）：网络层、大厅与多人画面

> 分支 feat/net-wire，2026-11-10 夜 ~ 11-11 凌晨，**暂拟，待评审确认**。模拟层的多人规则（倒地救援、按人数加强、多人商店、中途加入、托管、整局存档）
> 在 net-sim 那条线，见 `docs/design.md`「4. 联机」和 `src/sim/coop.ts`、`roster.ts`、`snapshot.ts`。这一页只讲网络、同步和界面。

## 一句话

**房主权威 + 中继**：全部模拟在房主的浏览器里跑；中继（`server/relay.mjs`）只管房间和转发；其他人只发操作、收状态，画的是一份「镜像世界」。
单人就是「没有其他人的房主」——不进大厅时走的还是原来的路，一行网络代码都不跑。

```
 其他人 ──操作（30 次/秒）、商店指令──▶ 中继 ──▶ 房主（跑 step）
 其他人 ◀──状态差量 + 事件（20 次/秒）── 中继 ◀── 房主
```

## 在局域网里玩（电脑 + 手机，同一个 Wi-Fi）

1. 电脑上开两个终端，都在项目目录：
   - `npm run relay`（中继，端口 5300；启动时会打出本机的局域网地址）
   - `npx vite --host --port 5180 --strictPort`（游戏；`Network:` 那一行就是手机要打开的地址，例如 `http://192.168.1.23:5180/`）
2. 电脑浏览器打开 `http://localhost:5180/` → 标题页「联机」→ 名号随意 →「建房」，得到四位房间码（字符里没有 0 / O / 1 / I / L）。
   房间页上的分享链接会自动换成局域网地址（中继的 `/info` 告诉它本机的地址）。最省事的是按「二维码」，**手机用相机扫一下**就打开、直接进房；
   也可以按「复制」发给手机（微信里点开即可），或者手机上直接打开 `http://<电脑的局域网地址>:5180/?room=房间码`。
   也可以手机打开游戏首页 →「联机」→ 输入房间码 →「进房」。
3. 手机上按「准备」，电脑上（房主）按「开始」，一起进第一波。最多 4 人；一个人也能「开始」（等于单人，但走联机的路）。
4. 第一次跑 `npm run relay` 时 macOS 可能弹「是否允许 node 接受传入网络连接」，选允许；不然手机连不上中继（症状：手机上大厅里一直「正在连中继…」然后报「连不上中继」）。
   公司网络、开了 VPN 时局域网地址可能不止一个，分享链接取的是 192.168 开头的那个优先。
   局域网地址随网络变化，以 `npx vite --host` 打出来的 `Network:` 那一行为准。

中继的地址默认是「打开页面的那台机器的 5300 端口」，网址参数 `?relay=主机:端口`（或完整的 `ws://…`）可以改。
上了公网（页面是 `https://域名/`，或者 http 但用默认端口打开）就连同一个域名的 `wss://域名/relay`，由反向代理转给中继——见 `docs/deploy.md`。

测试用的网址参数：`?online` 打开就是大厅；`?room=ABCD` 打开就进那个房（刷新页面也回到原来的位置）；和 `?bot` 一起用时进了局由机器人替自己打（其他人开 `?bot` 时机器人读的是镜像世界）；
房主开 `?wave=7` 时从第 7 波前的商店开局（所有人都带 999 灵石）。

## 由哪些部分组成

| 文件 | 做什么 |
|---|---|
| `server/relay.mjs` | 中继：Node + `ws`，监听 `0.0.0.0:5300`。房间码、名单、转发、心跳与掉线、房主迁移、限流；`/health`、`/info`（本机局域网地址）、`/stats`（各房间实际流量）。不存任何用户数据，日志只打建房、进出、掉线、换房主 |
| `src/net/protocol.ts` | 消息格式（TS 类型）：和中继之间的控制帧、房主 ↔ 其他人的游戏消息 |
| `src/net/link.ts` | 和中继之间的一条连接：建房 / 进房 / 离开、名单、断线自动重连（带凭据回到原来的位置）、心跳、到中继的往返延迟 |
| `src/net/codec.ts` | 世界状态的编码：纯数据 + 差量（见下面「状态同步」） |
| `src/net/host.ts` | 房主这边：收操作和指令、每秒 20 次广播状态、存档、对名单（托管 / 回来 / 退出 / 中途加入） |
| `src/net/guest.ts`、`mirror.ts` | 其他人这边：发操作、收状态；镜像世界、插值缓冲、事件按帧号放、自己人物的预测与校正 |
| `src/net/session.ts` | 一局联机：连接 + 人物分配 + 现在是房主还是其他人（迁移时会变） |
| `src/game/lobby.ts` | 大厅（标题页「联机」）：建房、进房、名单、准备、开始、分享链接和二维码 |
| `src/game/qr.ts` | 二维码编码（字节模式、纠错等级 L、版本 1–5，不依赖库）：大厅里把分享链接画成二维码。测试 `qr.test.ts` 和标准的参照值对；开发时另用独立的解码器（jsQR）从截图里读回链接核对过 |
| `src/game/net-hud.ts` | 局内叠的一层：队友的小血条、角上的状态（延迟 / 流量）、提示（房主暂停、掉线、接手……）、万宝阁里「等谁出战」 |
| `src/game/feel.ts` | 主循环接线（带「联机」字样的几处）：房主多喂其他人的操作并广播；其他人不 step、画镜像；多个人物的画面与名字签；暂停、再战、迁移 |

动到的别人的文件（都是小改，单人行为不变）：`src/game/title.ts`（加「联机」按钮，第四个按钮的入场延迟）、`src/main.ts`（`?room=` / `?online`、把联机交给游戏、联机局不放开场过场）、
`src/game/technique-fx.ts`（法天象地的大身形、金刚不坏的金身按人画）、`src/game/pet-fx.ts`（缠住的布条记下是谁的混天绫）、`src/game/enemy-views.ts`（敌人朝最近的那个人）、
`src/game/fx.ts`（寒冰幡碎冰按房里任何人的器灵）。

## 中继协议

WebSocket 文本帧。**控制帧**是 JSON 对象：

| 方向 | 帧 | 说明 |
|---|---|---|
| → | `{t:'create', name, meta}` | 建房，成为房主 |
| → | `{t:'join', room, name, meta, token?}` | 进房；`token` 是上次在这个房间的凭据（刷新、断线重连回到原来的编号） |
| → | `{t:'meta', meta, name?}` | 改自己的附加信息（角色、准备了没有，≤ 300 字节的 JSON，中继不看内容） |
| → | `{t:'leave'}` / `{t:'abdicate'}` | 离开房间 / 房主让位 |
| → ← | `{t:'hb', c}` | 心跳（客户端约 2 秒一次，中继原样回声，顺便量往返延迟） |
| ← | `{t:'joined', room, you, token, host, members}` | 进房成功 |
| ← | `{t:'room', host, members}` | 名单变了（每人：编号、名号、附加信息、连着没有、进房顺序、是不是房主） |
| ← | `{t:'host', id, prev, why}` / `{t:'hostAway', id, wait}` | 换房主了 / 房主掉线、等 `wait` 毫秒再迁 |
| ← | `{t:'err', code, msg}` | `no_room` `full` `bad` `busy` `rate` `size` |
| ← | `{t:'bye', msg}` | 中继要关了（更新、重启；收到 SIGTERM 时发）：房间都在中继的内存里，重启后就没了——客户端直接当「房间没了」，不再重连回这个房；随后中继用 1012 关连接 |

**数据帧**（游戏消息）不解析、原样转：客户端发 `>目标|内容`，中继发出去是 `<来源|内容`。房主发：目标为空 = 其他所有人，数字 = 那一个人；其他人发：一律给房主。

- 房间：4 位码（字母表 `ABCDEFGHJKMNPQRSTUVWXYZ23456789`），最多 4 人，成员编号在一个房间里只增不复用；掉线的人位置留 10 分钟；房里一个连着的人都没有了，60 秒后删房。
- 掉线：6 秒什么都没收到就算掉线（手机切后台时 JS 停了、TCP 不一定马上断）。
- 房主掉线：**关页面 / 刷新（浏览器发 1001）立刻迁**；别的掉线先通知所有人「房主不在」、等 24 秒（加上 6 秒的检测，全房最多等约 30 秒）再迁，期间回来了就不迁。
  迁给谁：按进房顺序，第一个连着的人。迁移的游戏逻辑在客户端（新房主从存档重开这一波）。
- 不信任客户端：房间码以外只认格式；名号去控制字符、最多 12 字；附加信息 ≤ 300 字节；控制帧 ≤ 4 KB；其他人的数据帧 ≤ 16 KB、房主的 ≤ 1 MB；
  限流（令牌桶）其他人每秒 80 条（可攒 160），房主每秒 300 条，超了丢掉、每秒提醒一次；同一个 IP 最多 24 条连接。
- 压缩：开了 permessage-deflate（等级 3，256 字节以下的帧不压），浏览器自动协商。
- 环境变量：`RELAY_PORT`、`RELAY_HOST`；上公网用的来源白名单、房间 / 连接上限、反向代理、日志格式等见 `docs/deploy.md`「中继」；测试用的 `RELAY_SILENCE_MS`、`RELAY_HOST_GRACE_MS`。

## 游戏协议（房主 ↔ 其他人）

房主发：`start`（开局 / 再战 / 迁移后接着打：种子、人物分配）、`st`（状态，见下）、`save`（整局存档）、`slots`（人物分配变了）、`pause`（房主暂停 / 继续）、`pong`、`wait`（这一局正在打，等到商店）。
其他人发：`in`（操作）、`cmd`（商店指令）、`ping`、`sync`（要一份整的状态）、`again`（陨落后按了再战）、`hello`（刚进房，在大厅里）。字段见 `src/net/protocol.ts`。

- **操作** `{t:'in', r, s, x, y, k}`：最多每秒 30 次，变向与神通最多等 33 毫秒。`r` 是本局种子，用来过滤上一局滞留的消息。`k` 是「一共按过几次神通」，数字涨了就是又按了一次，不会漏。房主用每人最新的一份；400 毫秒没更新就当他松手了。
- **商店指令** `{t:'cmd', r, c}`：随点随发；房主按白名单查字段的类型和范围，`player` 一律改成发的人自己的位置。
- 人物分配：开局时房主第一（0 号），其余按进房顺序；中途加入的人复用离开的人留下的格子（`roster.addPlayer`）。

## 状态同步

**房主**每秒约 20 次广播一份 `{t:'st', k, n, b, r, d, a, p}`；事件单独可靠发送为 `ev`。`b` 指向确认基线，具体解码与缓冲以本文协议 5 记录为准：

- `k` 模拟的帧号；`n` 递增的传输序号（模拟暂停或结束时仍递增）；`r` 本局种子；`d` 世界状态相对上一份的**差**；`e` 这段时间的事件（`[距这一份几帧, 事件]`）；`a[i]` 房主已交给模拟的第 i 个人的最新操作序号；`p[i]` 第 i 个人此刻的位置。
- 编码（`codec.ts`，通用的、不认识游戏规则——模拟层加的纯数据字段自动就同步过去）：
  - 先转成纯数据：去掉随机数、Set / Map，坐标一位小数、别的数两位小数；`px / py / pa`（上一帧的值）不发，镜像那边自己补；
    表现层不读、又每帧都变的运行时字段列在 `SKIP` 里不发（法宝的冷却、敌人的击退速度、宠物的瞄准点……）。以后表现层要读其中某个字段，从 `SKIP` 里删掉就行；
  - 再和上一份比：对象只发变了的键；带 id 的数组（敌人、圈、灵石、区域……）按 id 对，新增 / 变了的、没了的分开发，**位置单独打包成一串整数**（`[id, x×10, y×10, …]`）；
    前掉后接的数组（风火轮的火痕）只发两头；别的数组变了整个换。
  - WebSocket 可靠有序、中继按顺序转；仍用 `n` 检查差量是否连续，发现缺口就请求整份，避免永久错位。刚进来的、重连的发 `sync` 要一份整的（从空对象开始的差）。
- 每一波开打时、商店打开时、开局时，房主还发一份 `save`（`sim/snapshot.ts` 的整局存档，逐位精确，四人刚开波约 8 KB），迁移房主用。

**其他人**（`mirror.ts`）：

- 不推进模拟。收到的差按顺序打到镜像世界上，**画面落后房主约 100 毫秒**（6 帧；网络抖得厉害时自动加，最多 12 帧）：
  画的时刻落在两份状态之间，`px / py` 是前一份、`x / y` 是后一份，`alpha` 是两份之间走了多少——表现层本来就按 `alpha` 插值，所以特效、界面都不用改。
- 事件带着帧号，画的时刻走到那一帧才交给特效、界面、音效（和画面对得上）。自己暂停了一阵再追上来时，过时半秒以上的命中、击杀不放（开波、商店、陨落这类管流程的照放）。
- **自己的人物先按本地操作走**（和 `world.step` 一样的走法：移速、魔气减速、外沿是硬边界），手感不黏；收到房主的状态后，
  房主已经处理到第几个操作、之后的那些还没算进去——加上它们就是「现在应该在哪」：每个渲染帧只按最新状态校正一次，小误差以 60 毫秒的时间常数平滑消化，差 32 像素以上直接对齐。
  镜像里自己的位置换成预测的位置，所以跟着人物走的法宝、光环、镜头都跟着它。
- 商店：每人看自己的（万宝阁按 `players[自己]` 画），指令发给房主执行，结果随下一份状态回来并立即应用，不经过战斗插值。联机普通波结束后不等待各端旁白，直接进入商店。
- 积压较多时追到目标缓冲位置；差量链仍完整应用，只为最终插值区间遍历位置一次。超过 30 份积压则请求补全，等待期间最多每两秒重试一次。补全保留尚未确认的本地移动，新局与重入才重置输入序号。

## 2026-11-19 公网联机修复与验证

用户报告普通波后队友商店出现晚、天赋点击无效、再战后移动回弹。双浏览器与回归测试发现：

- 公网旧版曾测到约 1.8 秒往返延迟；局域网低延迟时点击能生效，因此不能把所有情况都归因于按钮。
- 暂停导致积压时，旧补全逻辑连续发出 19 次请求；新逻辑只发一次，并清空失效差量。
- 旧输入确认的是“收到”，不是“用于模拟”，会过早丢掉未确认的移动。重入还会保留旧序号，使新输入被拒绝。
- 用模拟帧去重会丢掉同一帧的结束状态；现改用独立传输序号，并隔离旧局消息。
- 快速变向原先允许每 12 毫秒加发输入，可能超过 Java 中继每秒 40 条的额度；现限制输入每秒 30 份，保留心跳和指令余量。

验证脚本 `tools/net-comfort.mjs`：真实双浏览器点击功法、天赋和准备按钮，两次普通波走实际 collect→shop 流程（调试时仅提前波末计时），再战两次后各向右移动两秒。`--cloud` 从本地 dist 给浏览器加载 Pages 生产产物，实际连接公网测试中继，不修改线上文件。

两轮公网验证均完成，未出现脚本异常。第二轮末次再战，队友两秒移动约 160 像素，预测误差 4.3 像素，往返约 233 毫秒。这是单次样本，不代表所有设备的表现；本轮针对同步算法，不以此宣称整体帧率提升。

同步回归位于 `src/net/sync-regression.test.ts`。日志和真实阶段截图保留在本地忽略目录 `scratch/net/`。更新后全员刷新并重新建房；协议版本为 2，大厅会提示版本不一致。Java 服务和 Nacos 无需因本轮前端修改重新部署。

## 带宽与延迟（实测）

**无界面测量**（`node tools/net-bandwidth.ts 4 18 5`：4 个人的机器人局、种子 5，打到第 18 波；按「发给一个人」算，房主只发一份、中继转给每个人）：

| | 压缩前 | 压缩后（permessage-deflate 等级 3） |
|---|---|---|
| 整局平均 | 55 KB/s | 16 KB/s |
| 战斗波最高（第 16–17 波，场上约 175 只敌人） | 108 KB/s | 32 KB/s |
| 第 1 波 / 第 5 波 / 第 10 波 | 19 / 46 / 74 KB/s | — |
| 首领战（第 6 / 12 / 18 波） | 25 / 37 / 45 KB/s | — |
| 商店 | 约 5 KB/s | — |

最大的一条约 35 KB（压缩前），整份状态约 10 KB。房主每次编码（纯数据 + 差量 + JSON）在这台 Mac 上中位 0.45 ms、95% 0.67 ms（第 14 波以后、178 只敌人、4 人），
每秒 15 次合计约 7 ms，手机当房主慢几倍也只占几个百分点。优化前（每次都重发每个人的整个法宝列表、位置不打包）整局平均 87 KB/s、最高 167 KB/s；最早的整份 JSON（不做差量）两个人就要约 140 KB/s。

**浏览器实测**（三个页面挤在一台 Mac 上，软件渲染、每个页面约 8–11 帧，所以延迟和抖动比真机差得多）：

- 两人、第 1 波：房主上行平均 6.7 KB/s（压缩前）；往返延迟平均 30 ms（含页面卡顿）；画面落后房主约 5 帧（83 毫秒）；预测校正平均 0.3 像素。
- 三人、第 7–8 波：中继实测（`/stats`，TCP 层、压缩后、含帧头）进 3.9 KB/s、出 8.6 KB/s（出 = 发给两个人的总和），最高进 11.6、出 27.1 KB/s。

局域网里完全够用；以后上公网再看要不要做设计文档里说的「敌人本地推演、低频校正」。

## 掉线、迁移、进出

| 情况 | 怎么处理 |
|---|---|
| 其他人断网 / 切后台 | 中继 6 秒判掉线 → 房主 `setAway`：机器人替他打（`bot.botTurn`）、受伤减半、商店里替他买、替他按出战；名单、名字签上标「托」。他的连接自己重连（回前台超过 4 秒直接重连），回来后要一份整的状态接着打 |
| 其他人关了页面又点链接回来 | 凭据在标签页里（`sessionStorage`），关了就没了，中继当他是新来的；房主按**名号**对上一个掉线的人物，就把那个人物还给他 |
| 刷新页面 | 带着凭据回到原来的编号，房主把他接回这一局 |
| 其他人退出（回到标题） | `removePlayer`：人物从场上消失，格子留着给之后中途加入的人 |
| 打着的时候有人进房 | 大厅里提示「这一局正在打：等到万宝阁就把你加进去」；商店一开，房主 `addPlayer`（基础起手、灵石给在场的人平均数的六成），发给他开局消息，他进局逛商店、按出战 |
| 房主打开暂停面板 | **全房暂停**（模拟就在房主那里）：其他人看到「房主暂停了」。其他人打开暂停面板只是他自己的面板，局照常在打，他的人物原地不动 |
| 房主切到后台 | 先告诉大家暂停；电脑上后台的页面还在跑定时器，30 秒还没回来就自己让位；手机上 JS 停了，中继 6 秒判掉线，再等 24 秒迁 |
| 房主关页面 | 中继立刻把房主交给下一个人 |
| 房主断网、页面冻住 | 其他人看到「房主掉线了 · 还剩几秒换人」；24 秒内回来就接着打，不回来就迁 |
| 迁移 | 新房主从最近一份存档（这一波开始时，或者商店打开时）`restore`、重开这一波，告诉大家「接手房主 · 从这一波开始重打」；原来的房主那一格交给机器人托管；他回来时变成其他人（重连时才知道换了房主的也一样） |
| 房主自己连不上中继 | 停下模拟（其他人看不到、操作也到不了，接着打只会让他们白白挨打），连上后先发一份整的 |
| 陨落 | 谁按「再战」都行：房主换个种子重开，大家一起回到第一波 |

## 2026-11-20 联机协议 5

模拟保持 60Hz，渲染上限保持 60fps，状态发送目标改为 20Hz。新旧协议在大厅不能混用。首次整份可靠送达，未确认时最多每 200ms 重发，防止启动阶段重复大包。

状态新增 `b`，指向已确认的基线序号；`n` 仍是传输序号。队友把成功解码的 `ack` 合并进 30Hz 操作和 ping，不增加独立高频 ACK 消息。房主选择在线玩家共同确认的基线，只广播一份，保持 Java 的 60Hz 房主消息额度；双方保留最多 64 份基线。基线缺失时要求补全，不能把差量套在错误状态上。不可变解码只复制变化分支。显示积压可合并过时状态，完整状态不依赖所有中间包。

事件独立使用可靠消息 `ev`，携带局种子、事件批次序号和 tick。传输切换不重复播放；事件不随位置快照丢弃，商店结果立即应用。暂停、存档、开局、再战与商店指令继续可靠传输。

插值时间轴在两份快照之间持续前进，缓冲依据近期到达抖动的高分位调整，100–200ms 范围内缓慢变化。短时空窗最多外推 100ms，后续用 80ms 时间常数校正显示位置；真实瞬移不拖尾。显示预测每帧还原，不写入确认基线、不计算伤害或碰撞。位置索引只在新显示状态时更新，渲染帧复用记录，避免每帧遍历所有字段与分配 Map。

哪吒保留原即时神通表现；其他角色新增即时起手光效、音效和提示，完整神通方向和伤害仍由房主确认。确认后不重复播放起手音效与提示。

默认公网连接在后台尝试 STUN 辅助直连，失败继续中继，断开自动回退。公网可靠事件一直使用中继，状态、输入与 ping 在直连可用时走无序、无重传通道。严格局域网模式不使用 STUN，可靠消息也走直连。状态分片允许乱序、限时重组，最多缓存 4 条，过期 300ms；消息与连接积压仍有界。WebSocket / 状态通道超过 64KiB 积压时跳过可替代状态，可靠指令不丢。未部署 TURN，不保证所有公网 NAT 都能穿透。

输入预测区分已经发送与尚未发送的操作，未发送的转向归到下一份输入，旧 ACK 不会撤销最新本地操作。预测使用最新确认的移速与边界，避免拿延迟显示状态计算自己的移动。

房主正常保留约 24 份近期状态与正在使用的基线。新加入或长期不确认的队友单独补全，避免拖住其他人的共同基线。超过 64KiB 的大状态改用可靠通道，避免大量分片丢失导致长期收不到状态。

真实 Java 中继下，协议 5 的中继 / 严格局域网分别通过普通波商店、两次再战与移动验证。自动直连、断开后回退，以及候选地址全部被阻断仍能开局，均通过浏览器验证。四人混合连接（两名直连、一名中继）持续推进并共同进入商店。构建与类型检查通过，648 项自动测试通过。

人工有序突发测试使用固定种子、相同波次，加入 60ms 延迟及周期性约 200ms 空窗，直接读取远离本机角色的世界精灵位置；旧版约 21.0% 的采样帧停住，新版约 2.4%。两次 p95 帧耗时均约 25ms，不能据此声称整体 FPS 提升；机器人输入与场景实体数量会随同步行为改变，此结果仅是该故障注入样本。额外每十份状态丢一份时，新版仍持续推进。测试脚本 `tools/net-jitter.mjs`，快照丢失用 `GAME_TEST_LOSS=1`。

真实多设备、不同运营商及严格 NAT 网络仍需试玩确认。
