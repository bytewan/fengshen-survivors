# 低端手机性能（M4，2026-11-11，分支 feat/perf）

2026-11-20：协议 5 的人工有序突发样本中，可见世界精灵停顿采样比例约 21.0% → 2.4%；p95 帧耗时仍约 25ms。这是网络显示连续性的改善，不是全设备 FPS 测试。显示预测每帧复用索引和记录，仅在状态变化时更新索引；历史快照有界。条件与验证见 `docs/netcode.md` 协议 5 记录。

> 目标（`docs/plan-m2-m4.md`「M4」）：低端安卓上（用 CPU 降速 4–6 倍模拟）最重的场景稳在 50–60 帧，不卡顿、不掉成一顿一顿；电脑上画面不变差。
> 结论先说（数字见「改动前后」）：手机横屏、6 倍降速下，三个首领战和敌人最多的那一波（第 15 波 · 劫五）改动后都是 59–60 帧、没有长任务；
> 两人联机的跟随者从 50 帧升到 55 帧（低档 57.5 帧），**还没稳在 60**；
> **满场 280 只没达标**：这是脚本一直补怪到模拟上限造出来的压力场景，4 倍降速从 31 帧升到 51 帧，6 倍降速从 16 帧升到 28 帧（低档 36 帧），仍然不到 50。
> 高档画面和改动前肉眼一样（`?fxlab` 全部法宝逐张比过，见下面「画面一致性」）。

## 怎么量

### 实时量（`tools/perf-probe.mjs`，进仓库）

```
node tools/perf-probe.mjs [--port 5252] [--scenes boss1,yao,boss3,horde,swarm,net] [--sizes phoneL,phoneP,desk] [--rates 4,6]
                          [--secs 20] [--warm 6] [--runs 3] [--paths /,/scratch/perf-base/] [--quality high|low|auto] [--profile] [--soft]
```

- Playwright + CDP 的 `Emulation.setCPUThrottlingRate`（4、6 倍）模拟低端安卓的 CPU；显卡用真的（ANGLE Metal；降速只作用在页面主线程上，显卡那边的活另说，见「显卡那一边」）。
- 尺寸：`phoneL` 手机横屏 844×390@3（触屏）、`phoneP` 竖屏 390×844@3、`desk` 电脑 1280×720。
- **60 Hz**：这台 Mac 的屏幕是 120 Hz，无头 Chromium 的 requestAnimationFrame 也是 120 次 / 秒；脚本在页面里把它卡成「离上一次回调不到 12.5 毫秒就再等一个同步」
  （`--hz 60`）：平时隔一个同步回调一次，就是 60 Hz；一帧没做完，下一次最早在 25 毫秒，算掉帧。
  （一开始按「偶数个同步」卡，屏幕的实际刷新率不是正好 120 时奇偶会漂，把没掉的帧也算成掉帧——那一版的掉帧比例作废，表里的都是改过之后量的。）
- 场景（都开 `?bot`：机器人替人打，模拟的种子固定为 7；`Math.random` 也固定种子；进了波次之后人物锁血）：
  | id | 网址 | 说明 |
  |---|---|---|
  | `boss1` | `?bot&wave=6` | 第一章首领魔化哪吒。首领的血先压到第三阶段的门槛下面（三位首领的门槛都是三成），量的是最重的最后一段，之后首领的血不低于一成五 |
  | `yao` | `?bot&wave=12` | 第二章首领姚天君 + 十阵，同上第三阶段 |
  | `boss3` | `?bot&wave=18` | 第三章首领，同上第三阶段 |
  | `horde` | `?bot&wave=15&jie=5` | 第三章第 3 波 · 劫五（任务给的「敌人最多」那一波） |
  | `swarm` | 同上 + 一直补怪到 280 只 | 模拟的同屏上限（`SPAWN.maxEnemies`）；刷在 250–320 像素外往人身上涌——打不动的玩家在劫五会遇到的满场 |
  | `net` | 房主 `?online&bot&wave=15&jie=5`，跟随者 `?room=…&bot` | 两人联机，量跟随者那边（房主不降速）；脚本自己在 5353 起中继 |
- 进了波次后降速、预热 `--warm` 秒、量 `--secs` 秒。记：每帧 Pixi 时钟 `update` 的耗时（feel.ts 的整帧 + 提交渲染）的中位 / p95 / p99、帧率、
  掉帧（帧间隔 > 20 毫秒的比例）、顿（帧间隔 > 50 毫秒的次数）、长任务（> 50 毫秒）、每帧 WebGL 绘制次数和贴图上传次数、JS 堆、纹理张数、显示对象数，
  以及 CDP 的主线程累计（脚本、样式、排版、任务，换算成每帧）。`--profile` 另录一份 CPU 采样。
- **同一时刻前后对比**：这台机器上同时跑着好几条线，负载忽高忽低（同一份代码两次能差三成）。`--paths` 让同一个开发服务器上的两份代码轮流量：
  `/` 是当前工作区，`/scratch/perf-base/` 是改动前的快照（`git archive $(git merge-base HEAD main) src vendor index.html`，把 index.html 里的入口改成
  `/scratch/perf-base/src/main.ts`）。`--runs 3` 按「第 1 轮两份、第 2 轮两份……」交错着跑，每份取三轮的中位数。

### 确定性跑分（`scratch/bench.mjs`，没进仓库）

找热点、判断一处改动有没有用时用它：页面里的 requestAnimationFrame 全挡掉，游戏的时钟从头到尾手动推（每次正好 1/60 秒、一帧一步模拟），
补怪用自己的固定种子——同一份代码每次跑的活一模一样，截图逐像素一样；前后两份代码的差别只来自代码。量的是每帧 `ticker.update` 和其中 `renderer.render` 的耗时，
`--shot` 截画布（界面那一层按真实时间淡入淡出，截图时藏起来）拿去逐像素比，`--profile` 录 CPU 采样。不降速时噪声最小，用来比改动；降速的数字以实时量为准。

### 页面里的自查（`?perf`，进仓库）

网址加 `?perf`：画面左上角一行 `fps · 整帧平均 / p95 · sim fx scn ui draw（各段毫秒）· 画质档`，**手机上也能看**（用户试玩时可以打开看真机的数）。
脚本里 `__feel.perf.stats(n)` 读最近 600 帧：各段平均、最慢 n 帧的各段明细（含那一帧推了几步模拟、出了多少事件）、每个特效模块的 update / onEvent 平均和最慢一次
（`src/game/frame-probe.ts`；平时关着，每段只多一次布尔判断）。

## 热点和修法（一处一处修、每修一处重量一次）

先用 CPU 采样和 `?perf` 拆开一帧：Pixi 渲染约占主线程忙时的 45%（其中每帧把整棵场景树的变换重算一遍、每帧重建绘制指令最多），表现层各模块约 40%，模拟 5–12%。
卡顿的那几帧（`scratch/spikes.mjs`：把超过 25 毫秒的帧和 CPU 采样对齐）是「第一次用到才现做」的东西和垃圾回收。

| # | 热点 | 修法（只换实现，样子不变） | 文件 | 效果（确定性跑分，不降速） |
|---|---|---|---|---|
| 1 | 镜头每帧挪世界层，Pixi 8 就把底下几千个节点的变换全重算、顶点全重写 | 世界层、辉光层改成渲染组（render group）：镜头挪的是整组的变换，在显卡上乘；辉光层的加法混合留在里面那一层（渲染组的根不往下传混合方式） | `src/render/stage.ts` | 满场渲染 −15% 左右 |

## 画质档

设置里「画质：自动 / 高 / 低」（`src/render/quality.ts`；这台设备自己的，存在 localStorage `fs.v1.quality`，不进存档码——电脑和手机该用的档不一样）。

- **高**：就是原来的画面（下面「画面一致性」）。
- **低**：只动不影响判断的东西
  - 画布的后备缓冲按「不超过需要的」整数倍放大（`view-fit.ts` 的 `lowRes`）：手机横屏 844×390@3 从 2400×1350 降到 1920×1080，剩下那一点由浏览器放大，像素边上略软；
  - 魔气里翻滚的烟团不画（每帧省一遍离屏贴图 + 遮罩；魔气的底色、浓淡照旧，边界一样看得清）；
  - 成团迸出的装饰粒子少一些：一次超过三粒的按倍率减（一次三粒以内的照旧——预警、拖尾这类一粒一粒冒的不减）；
  - 打死、命中、暴击的修仙版特效（xfx.ts）同屏上限减半（满了照旧退回原来的画法）。
  - **不减的**：地上的预警红光、首领的出招、冻住 / 减速 / 眩晕 / 破甲的修仙版状态、灼烧的火苗、伤害数字、屏幕震动、光照图。
- **自动**：先按高档；这台设备上打着打着掉帧（连着两段、每段三秒里超过一成五的帧间隔超过 22 毫秒）就换成低档并记下来（`fs.v1.autoQuality`），
  以后自动就直接是低档；内存很小的安卓（`navigator.deviceMemory ≤ 2`）一开始就是低档。手动选一次高 / 低就以手动的为准（再选回自动会重新量）。
- 不管哪一档，掉帧时装饰粒子的倍率再往下压（每段 ×0.7，最低 0.25），帧率回来再每段 +0.1 放回去——不掉帧的电脑上倍率永远是 1，不多取一个随机数，画面和原来一模一样。

为什么不关光照图：它除了暗角还有第二章的黄昏、第三章的月光（乘到整个画面上的颜色），关掉以后场景的颜色就变了；它每帧只是一遍 480×270 的离屏贴图，省不了多少。

## 显卡那一边

CPU 降速模拟不出手机显卡慢。估算：画面先画进 480×270（每层的填充都很便宜），最贵的是最后那一步——整数倍放大到后备缓冲（手机横屏 2400×1350 = 324 万像素）
再由浏览器缩到屏幕。低档少放大一档（1920×1080 = 207 万像素，少 36%）。每帧绘制次数 20–60 次（`draws`）；改动后多了几次（渲染组、粒子层各占一次），对显卡无所谓。
逐像素的层（PixelGraphics、法宝的 Pixels）每帧只上传画过的行（最多 480×270×4 = 0.5 MB）。

## 画面一致性

- `?fxlab` 全部 30 组（27 件公共法宝 + 相生、状态、合体）× 凡品 / 神品，每组从头放起、每 0.12 秒拍一张、12 张一组（`scratch/fxlab-ab.mjs`；最后一次是在合完 main 的 ba09b60 之后跑的）：
  - 和「改动前 + 只加渲染组」比：**全部逐像素一样**（60 组都是 0 个像素不同）——渲染组以外的改动（粒子层、像素缓冲、插入排序、预热……）画出来一模一样。
  - 和改动前比（抽了 10 件 × 两个品阶）：每组 0.3%–2.6% 的像素不一样，都是**恰好落在半像素上的小精灵**（奇数宽、锚点 0.5 的火苗、火圈的点、几颗灵石）取整方向变了：渲染组让镜头的平移在显卡上乘，
    浮点误差的方向跟原来不同，`roundPixels` 对恰好 .5 的位置取整就可能往另一边。差一像素、肉眼看不出（对照图 `scratch/shots/fxlab-compare-*.png`，
    逐组的图在 `scratch/shots/fxlab/`）。原来就有这个问题（同一个精灵在画面不同位置取整方向也不一样），只是换了一种分布。
- 游戏里（确定性跑分截画布）：第三章第 3 波和「改动前 + 渲染组」比只差 0.16%（几颗灵石的半像素取整）；满场 280 只差 0.04%；姚天君那一波的差别和同一份代码自己跑两次一样
  （那一波有按真实时间走的东西）。
- 低档：`scratch/shots/high-phoneL.png`（高，2400×1350）和 `scratch/shots/low-phoneL.png`（低，1920×1080），同一局同一帧；放大对照 `scratch/shots/low-vs-high-crop.png`
  （低档下预警的红光、地上的黄带、火圈、冰、人物都在；火星少一些、魔气里没有翻滚的烟团）。

## 还没做的、拿不准的

- **满场 280 只在 6 倍降速下不到 50 帧**（高档 28、低档 36；4 倍降速 51；装满新法宝再满场是高档 26、低档 34.5）。剩下的大头是模拟本身（满场时每帧要推一到两步，降速后一步就好几毫秒）和各件法宝的表现层；
  模拟这一轮不能碰。正常打的时候同屏到不了 280 只（第 15 波 · 劫五机器人打下来是 35–45 只），打不动、被围住的玩家才会遇到。
- **两人联机的跟随者** 6 倍降速 55 帧（低档 57.5），每帧主线程中位 12.8 毫秒：比单人多出来的是每秒 15 次整份状态的解析和镜像世界的插值。

- 真机：只在 Mac 上用 CPU 降速模拟过，没有真的低端安卓；用户可以在手机上开 `?perf` 看帧率和低档的样子。★
- 低档的取舍（软一点的像素、没有翻滚的烟团、少一点的火星）需真机试玩后确定。★
- 模拟（`src/sim`）在满场时占一成多，这一轮不碰（要逐字一致）；以后可以做不改结果的优化（空间网格、事件数组复用）。
- 联机跟随者每秒收 15 次整份状态，解析时分配不少（堆在 35–75 MB 之间来回）；带宽那条线以后做差量 / 二进制时顺带能省。
- `zhuxian-fx.ts` 的剑光、`fx-new.ts` / `fx-new2.ts` 各件法宝的逐像素画法、混天绫的布还是每帧现画。装满新法宝那一波 `fx-new2.ts` 仍占主线程忙时约 14%
  （四海瓶的浪头每帧摆上百个精灵、瘟雾每帧重画），6 倍降速高档 58.6 帧、低档 59.5 帧。
